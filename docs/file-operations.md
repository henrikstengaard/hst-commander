# File Operations

Copying, UAE metadata, moving, renaming, deleting, making directories, creating volumes, sorting the panes, selecting groups, searching and properties. Read this when working on any of them.

Paths are relative to `src/`. Part of the agent docs, see [`src/agents.md`](../src/agents.md).

## Common Rules

- The front-ends call `NavigationContext` methods; the work happens in extension methods on `IVolume` (`VolumeCopy`, `VolumeMove`, `VolumeDelete`, `VolumeContents` in `Hst.Commander.Core.Volumes`) that only use `IVolume` members, so they work between any two volumes.
- Long operations run on a background thread with volumes of their own from `OpenLocationAsync`, never the pane's volume. For local paths that's a new `LocalVolume`; images are opened again from their files (images inside images from the reopened image they're in); other providers get a new volume changed to the current path.
- `GetOperationEntries` returns the marked entries, or the entry under the cursor when none are marked (never `..`). Marks are cleared after a successful copy or delete.
- Progress is reported at most every 100 ms and at item boundaries.
- While cached writes of a disk are written, e.g. of a physical disk when its cache fills up and at the end of a copy, move or delete, the progress has `DiskWrite` (`DiskWriteProgress`) and the progress dialogs of both front-ends show "Writing to disk 12M/16M" instead of the current file, with the current file's bar following the write and the speed and ETA of the write (the delete dialog shows the percentage, and the speed and ETA of the write in place of its ETA); see [Writable images](volumes.md#writable-images).
- While a progress dialog is open, the progress is also shown outside the window, so it can be followed from other applications: on the taskbar button on Windows, on the Dock tile on macOS (GUI) and in the terminal's tab or taskbar button (TUI, see [Terminals](tui.md#terminals)). It's busy (indeterminate) until the first progress, then follows `CopyProgress.OverallFraction` or `DeleteProgress.OverallFraction` (the total, or the cached writes of a disk while they're written), is paused (yellow on Windows) while cancelling and is cleared when the dialog closes. `TaskbarProgressReporter` drives a front-end's `ITaskbarProgress` and passes on only changes of the state or the whole percent. Linux desktops show nothing in the GUI.
- Operations that can't run in a location (the drive list, a read-only image) have a `...NotSupportedMessage` property, which the front-ends show as an error instead of opening the dialog; the method itself then throws `NotSupportedException`.
- Created and renamed entries are selected once by `GetSelectedIndex` when the entries are listed again.

## Copying

- `VolumeCopy.CopyToAsync` first scans the entries (containers recursively) to know the total size, then copies. Both volumes are changed back to their starting directory afterwards. Containers are merged with existing ones.
- Items are copied in the order of the scan (containers before their entries), unless the source returns a read order for them (`IVolume.GetReadOrder`, e.g. a solid 7z or rar archive): then all containers are created first and the items are copied in the read order, so a solid archive is decompressed once instead of once per item. Otherwise a small file stored after a large one (e.g. a 7 KB file after a 2 GB disk image in the same solid block) would wait for the large one to be decompressed, with no progress shown, and the large one would be decompressed again when copied.
- Modified dates are kept: items right after they're written, containers after everything is copied, deepest first, because writing into a container changes its date. A destination throwing `NotSupportedException` for dates is ignored.
- Before overwriting an existing item, `CopyOptions.ConfirmOverwrite` is asked with an `OverwriteRequest` and answers `Yes`, `No` (skip; removed from the progress totals) or `All`. Without a callback items are overwritten. Destination directories are listed once to detect existing items, and the speed/ETA clock is paused while asking.
- `CopyOptions` also holds the filter (`EntryFilter`: `*`/`?` wildcards, several patterns separated by `;`, case-insensitive, applied to items only; containers are always copied) and an optional target name for copying a single item under another name.
- When a copy is cancelled or fails during an item, the destination stream is closed and the partial item is deleted; cleanup errors are ignored so the original error is kept.
- `NavigationContext.CopyAsync` resolves the destination text: the other pane's current path means that pane's location (which may be an image); otherwise a local directory (relative to the source's local directory, created when missing); a single file copied to a non-directory path whose parent exists is copied under that name. A path below the other pane's current path (e.g. `c:\disk.adf\dir1` while it shows `c:\disk.adf`) means that directory in its location, so entries dropped on a directory inside an image are copied into it; a missing directory throws `IOException`. Copying entries onto themselves or a directory into itself throws `IOException`.
- Files dropped on a GUI pane from another application are copied or moved by `DroppedEntries`: their paths are grouped by directory, each opened as a `NavigationContext` with the UAE metadata setting of the pane dropped on, and copied with `CopyAsync`/`MoveAsync`, so they work like entries of a pane (see [Drag and drop](gui.md#drag-and-drop)).

## UAE Metadata

Amiga names can contain characters other file systems can't (e.g. `*`, `?`, `#`), and protection bits and comments can't be stored outside Amiga file systems. Like Hst Imager, `VolumeCopy.TransferAsync` decides what to do from `IVolume.SupportsAmigaMetadata` of the source and destination. It's true for Amiga file systems and lha/lzx archives, and forwarded by the wrapping volumes (`NestedVolume`, `EntryVolumeProvider`, `SharedImageVolume`, `RdbVolume`, `VolumeListVolume`, `HybridDiskVolume`); false in partition lists.

| Source | Destination | What happens |
|---|---|---|
| Amiga | Amiga | Names copied as they are; `SetAmigaMetadata` before the modified date (containers last) |
| Amiga | other | Names, protection bits and comments are written as UAE metadata in the format of `CopyOptions.UaeMetadata` |
| other | Amiga | UAE metadata of each source directory is read; entries get their Amiga names, bits and comments; metadata files aren't copied |
| other | other | Metadata is read as for copying to Amiga and written as for copying from Amiga, so entries keep their Amiga names and metadata even without their metadata files |

- Formats (`UaeMetadataFormat`): `UaeFsDb` (default; WinUAE and FS-UAE; a `_UAEFSDB.___` file per directory, names needing it get `__uae___` + a safe name made unique with random characters), `UaeMetafile` (FS-UAE; a `<name>.uaem` text file next to the entry, names `%xx` encoded) or `None` (no metadata, invalid characters replaced with `_`).
- Windows reserved names (`CON`, `NUL`, `COM1`, ...) need a normal name on Windows. Entries with a usable name and default metadata get no metadata. Existing metadata in the destination is kept, and an Amiga name copied again keeps its normal name.
- `UaeMetadataWriter` writes through `IVolume` only: metafiles right away, `_UAEFSDB.___` files after all items (also when the copy fails or is cancelled).
- `UaeMetadataReader` reads `_UAEFSDB.___`, on Windows also the version 2 nodes WinUAE writes as NTFS alternate data streams of local entries, plus valid `.uaem` metafiles. Invalid or unreadable metadata files are copied as normal files.
- `UaeMetadataUpdater` keeps metadata up to date in volumes that don't store Amiga metadata:
  - **Renaming:** the entered name is the new Amiga name. Only `/`, `\` and control characters are invalid (also `:` when the name needs metadata). An entry with metadata gets a normal name for the new Amiga name, keeping its bits and comment (alternate data streams are replaced by the format of the setting); an entry without metadata is renamed as usual unless the name can't be stored (e.g. `a*b` on Windows), then it gets a normal name and metadata. The normal name is selected.
  - **Deleting:** metadata of deleted entries is removed, also when deleting fails or is cancelled.
  - **Moving:** metadata of moved entries is removed from the source, so moved directories can be deleted. On the same local drive, nodes and metafiles move to the destination; entries that need it go through `VolumeMove.MoveToAsync`.
  - **Properties:** changing the protection bits of an entry with UAE metadata rewrites its node or metafile; an entry without it gets it, as when adding a comment.
- The panes show names as stored, e.g. `__uae___file_1`. The properties dialog shows the Amiga name and protection bits from the entry's UAE metadata, and the comment in its Comment tab.
- Entries of images dragged out of the GUI to other applications get the same names and metadata files as copying them to a local directory (see [Drag and drop](gui.md#drag-and-drop)).
- `None` turns all UAE metadata handling off: no reading, writing, updating or showing.
- The format is set in both front-ends' settings and passed to `NavigationContext.UaeMetadata` of both panes. Core references `Hst.Amiga` for the readers and writers.

## Moving and Renaming

- `VolumeMove.MoveToAsync` copies like `CopyToAsync` (sharing `VolumeCopy.TransferAsync`) and deletes each item right after it's copied. Containers are deleted afterwards, deepest first and only when empty, so skipped and filtered-out items stay in the source with their containers.
- `NavigationContext.MoveAsync` resolves the destination like `CopyAsync`. When both locations are local directories on the same drive and the filter matches everything (`*`, `*.*` or empty), entries whose name doesn't exist in the destination are moved with `File.Move`/`Directory.Move` (fast, no extra space); the rest go through `MoveToAsync`.
- A single entry moved to a plain name (no separator, not rooted, not the other pane's path and not an existing directory in the current location) is renamed instead: `GetRenameNameAsync` returns the name (null for a move) and `RenameAsync` renames on the pane's own volume, without a progress dialog. Names are validated like making a directory; another entry with the name throws `IOException`, case-only changes are allowed.

## Renaming

Shift+F6, or Rename in the context menu of the entries, renames the entry under the cursor (not the marked entries) in a dialog with its name filled in (in the GUI selected without the extension). `NavigationContext.RenameAsync` renames it like moving to a plain name (see above) and selects it. Both front-ends reuse their make directory dialog with another title and prompt.

## Clipboard

Ctrl+C, Ctrl+X and Ctrl+V (Alt+V in the TUI too, as Windows Terminal and the classic console paste text with Ctrl+V themselves), or Copy, Cut and Paste in the context menu of the entries (right-click), copy or cut the marked entries, or the entry under the cursor, to the clipboard and paste them in the current location of a pane.

- `EntryClipboard.SetAsync` opens the entries' location again as a context of its own (`NavigationContext.CloneAsync`, also reconnecting a connected location with its credentials), so they can be pasted after the pane has changed location, also from inside images. `EntryClipboard.Current` is shared by both panes and replaced by the next copy or cut. Cutting entries of a volume that can't move (e.g. archives) throws `NotSupportedException` with `MoveNotSupportedMessage`.
- Pasting doesn't ask for a destination, like Explorer: it goes straight to the copy or move progress dialog with the filter `*`, asking before overwriting as usual. Pasted cut entries are removed from the clipboard; copied entries can be pasted again.
- **Clipboard of the operating system:** the entries are also put on it, so other applications paste them, and files copied or cut in other applications are pasted like dropped files (`DroppedEntries`). `EntryClipboard.GetPasteSourceAsync` pastes `Current` while the clipboard of the operating system still holds what was put on it, otherwise its files.
  - **Windows** (`EntryClipboard.SetWindowsClipboard`, both front-ends): local entries as files (`WindowsFileClipboard`: `CF_HDROP` with "Preferred DropEffect"), so Explorer pastes them and moves cut files itself; whether the clipboard still holds them is told by its sequence number. Entries of images and other volumes go on it as virtual files (`WindowsVirtualFileDrag.SetClipboard`, the data object of [dragging out](gui.md#drag-and-drop)), so Explorer pastes them by reading them; whether the clipboard still holds them is told by `OleIsCurrentClipboard`. The OLE clipboard is set on a thread of its own pumping messages, as the application pasting reads the data object through messages to that thread: a console's main thread doesn't pump them, and the GUI's UI thread isn't blocked reading files. Files cut in Explorer are moved and the clipboard is emptied afterwards.
  - **Cut entries pasted in Explorer:** Explorer moves local files itself, so both front-ends check every second whether cut local entries have disappeared (`EntryClipboard.CheckCutMoved`, not while they are pasted in a pane) and list the panes again, emptying the clipboard when they are all gone. Cut entries of images are offered as virtual files with the move drop effect. Explorer copies them and reports the move to the data object, not with "Paste Succeeded" (delete-on-paste, which other applications may use) but with "Performed DropEffect" and, as it reads them on a thread of its own, `EndOperation` with the move effect (found by logging the calls of a real Explorer paste); then they are deleted from the image, the clipboard is emptied and the panes are listed again.
  - **macOS and Linux** (GUI): local entries are put on Avalonia's clipboard as files with an in-process marker, and pasting reads its files; entries of images are only pasted in the panes, and files are always copied.
  - The TUI only uses the clipboard of the operating system on Windows: a terminal can't put files on it elsewhere.
  - In terminals taking Ctrl+V for pasting text (Windows Terminal, the classic console), the TUI never sees Ctrl+V: when the clipboard holds files they paste their paths as text, if anything. Alt+V and the context menu paste instead.

## Deleting

- `VolumeDelete.DeleteAsync` scans first (entries inside a container before the container), then deletes in that order, using only `Delete` of items and empty containers. The volume is changed back to its starting directory, also when cancelled or failed. The progress has an estimated time left (`DeleteProgress.Eta`) from the average entries deleted per second, shown below the total bar.
- `NavigationContext.DeleteAsync` runs it on a volume of its own and removes the UAE metadata of deleted entries.

## Making Directories

`CreateDirectoryAsync(name)` creates the directory on the pane's own volume. The name is trimmed; empty, `.`, `..`, names with separators or invalid file name characters and existing names (case-insensitive on Windows) throw `IOException`.

## Creating Volumes

- F9 shows the list of `VolumeProviders.Creators`, then a dialog with the file name and the creator's fields (text/number fields as text, sizes as a number with a unit drop-down next to it (B, KB, MB, GB; `VolumeCreation.SizeUnits`, GB unless the default value is in a smaller unit), booleans as check boxes, choices as drop-down lists, required fields marked with `*` by `VolumeCreation.GetLabel`). A field with `EnabledByField` is disabled while that check box is unchecked (`VolumeCreation.IsEnabled`), and a disabled required field doesn't have to be entered. When creating fails, the error is shown and the fields dialog is shown again with the input kept.
- `CreateVolumeAsync(creator, fileName, input)` adds the extension when missing, validates the name like making a directory and converts the input with `VolumeCreation.GetValues` (trimmed, required fields checked, numbers parsed, sizes converted to bytes and may have decimals, defaults for missing input; `IOException` otherwise). Local files are created with `FileMode.CreateNew` and written on the thread pool, as sparse files when the creator has `CreatesSparseFile` (`SparseFile.TryMakeSparse`: marked sparse on Windows, which NTFS and ReFS support; on Linux and macOS setting the length leaves a hole where the file system supports it), otherwise, e.g. on FAT or exFAT, as regular files; elsewhere the volume is created in a temporary file and copied with `OpenWrite`. A partly created file is deleted on failure. The other pane is refreshed too.
- `AdfVolumeCreator` (Amiga plugin) creates an adf: `Volume name` (required, default `Empty`), `High density (1.76 MB)` (unchecked: 880 KB double density), `Format` (unchecked: all zeros, and the volume name, `Bootable` and `File system` are disabled and ignored), `Bootable` (writes the standard boot code with its checksum) and `File system` (`DOS0` to `DOS7`, default `DOS3`, FFS international).
- `ExFatVolumeCreator` (Disk plugin) creates an exFAT file system without a partition table (`.img`, opened by `FileSystemFileVolumeProvider`) as a sparse file: `Size` (required, default 1 GB, at least 1 MB, rounded down to whole 512-byte sectors), `Volume label` (up to 11 characters, empty by default) and `Cluster size` (`Default`: 4 KB up to 256 MB, 32 KB up to 32 GB, 128 KB above, like Windows; or 4 KB to 32 MB). It sets the length and formats with `ExFatFormatter`, ported from Hst Imager because DiscUtils' exFAT formatter writes an incomplete up-case table (e.g. `{` upper-cased to `Z`) and too small a FAT above 2 TB. Blocks of zeros aren't written, as the new file is all zeros, so only the parts of the boot regions, FAT, allocation bitmap, up-case table and root directory that aren't zeros take disk space. Tests check created volumes up to 4 TB with `ExFatValidator` (also from Hst Imager).

## Sorting the Panes

- Clicking a column header of a pane (Name, Size, Modified) sorts its entries by that column ascending, clicking it again descending (`EntrySort.Toggle`), with ▲ or ▼ after the sorted column's header (`GetHeader`), like the [search results](#searching). The panes are sorted by name ascending at first.
- `NavigationContext.Sort` is applied by `ListEntriesAsync`, so the order stays when navigating and refreshing. Each side's order is saved in the settings (`LeftSort` and `RightSort` in `tui-settings.json` and `gui-settings.json`, null for by name ascending) when a header is clicked, restored at startup, and moves with the pane's location when swapping panes (saved for the new sides). `ToggleSort` sorts the entries last listed again without listing them; the front-ends keep the entry under the cursor (and the GUI the icons already read).
- `..` stays first and directories stay before files. By name, the order the volume lists the entries in is kept (each volume sorts by name with its own comparison, and e.g. disks and partitions in their own order), reversed when descending. Equal sizes and dates (and directories without a size) are ordered by name.
- In the GUI the headers are only shown, and clickable, in the list navigation mode; the thumbnails and plugin modes use the same order.

## Selecting Groups

- Insert and Space toggle the mark of the entry under the cursor and move to the next entry; Shift+Down does the same and Shift+Up toggles and moves to the previous entry, so holding Shift with the arrows marks (or unmarks) a run of entries, like Norton and Total Commander (Terminal.app on macOS sends plain arrows for them unless set up, see [macOS Terminal](volumes.md#macos-terminal)). In the GUI's thumbnails and plugin navigation modes Shift+arrows, Shift+Left and Shift+Right too, move like the arrows (a row or an entry, the nearest icon).
- `MarkGroup`/`UnmarkGroup(entries, SelectGroupOptions)` add or remove marks of entries matching a filter (`CaseSensitive`, `FilesOnly`), keeping other marks; `InvertMarks` toggles every entry. `..` is never marked.
- `NameFilter`: a filter containing a regex character (`NameFilter.RegexCharacters`) is a regular expression matching any part of the name; otherwise wildcard patterns like `EntryFilter`, matching whole names. Empty matches everything; an invalid regex throws `IOException`.
- `+` selects, `-` unselects, `*` inverts. The keys are matched by the typed character so they work on any keyboard layout (plus the keypad keys). The filter starts as `*` and is remembered for the session, shared by select and unselect.

## Searching

Ctrl+S or File > Search (`CommanderActions.Search` for theme buttons) opens `SearchDialog` in both front-ends, searching from the active pane.

- **Options** (`SearchOptions`, in `EntrySearch.cs`): what to search for, a `NameFilter` (wildcards like `*.txt;*.md`, or a regular expression when it has a regex character or `Regular expression` is checked; empty or `*` finds all); `Start in`, filled with the pane's `CurrentPath` and resolved like the location dialog (`ChangeLocationAsync`), so it can be any local path, a path into an image or a path of the pane's volume provider; `Case sensitive` for names and text; `Contents` (`SearchContentType`: None, Text, Regular expression or Hex) with what to search the contents for; `Depth` (`SearchDepth`: all subdirectories, the current directory only, or a number of levels below it); and `Search in images and archives`. The options other than the start path are remembered for the session.
- **Searching** (`NavigationContext.SearchAsync`) runs on a background thread in a clone of the pane's context (`CloneAsync`, then the start path), never the pane's volume. It walks the clone's nested volume like `VolumeContents`, changing back to each parent in `finally`. Directories match by name only when not searching contents; with contents, only files whose names match are read. With images, files detected as images (`OpenImageAsync`, the same detection as Enter, including shared writable images and temporary copies of images inside images) are searched as a level too, closed with `GoParentAsync`. Linked local directories (symbolic links and junctions) are found but not searched, as they may link to a parent. Directories and files that can't be read are counted (`SearchProgress.Errors`) and skipped; an invalid name pattern, regex, hex value or start path throws `IOException`, shown as an error.
- **Contents** (`ContentMatcher`) reads a stream in 64 KB chunks keeping the end of the last chunk, so matches across chunks are found, and stops at the first match. Text is searched as UTF-8 bytes and, when it has characters 128-255, as Latin-1 too (Amiga and older files); case-insensitive text folds ASCII letters only. A regex is matched against the bytes read as Latin-1 characters (`Multiline`, so `^` and `$` match lines), keeping 4 KB (`RegexOverlap`): longer matches across chunks may be missed. Hex values are bytes like `DE AD BE EF`, `deadbeef`, `0xDE,0xAD` or `$4D-$5A`.
- **Results** (`SearchResult`) list as they're found in a table of path, size and modified date (`SizeText`, `ModifiedText`, like the panes), with the progress (`SearchProgress.Text`) at most every 100 ms; Search becomes Stop while searching and closing the dialog stops it. Clicking a column header sorts by it ascending, clicking it again descending (`SearchResultSort.Toggle`), with ▲ or ▼ after the sorted column's header (`GetHeader`); results found while searching are inserted in order (`IndexToInsert`), the selected result stays selected, directories come before files by size, equal sizes and dates are ordered by path, and the order is remembered for the session (by path ascending at first). The TUI shortens long paths at the start, keeping the name, and the GUI shows the full path as a tooltip. The results get the focus when a search with results ends; in the GUI, Up and Down outside the results (except in the levels box and the radio buttons) also move to them, e.g. right after Enter in a text box. Enter or double-click on a result, or `Go to`, closes the dialog and `GoToSearchResultAsync` changes the pane to the directory the entry was found in (in its volume provider, connecting again with the search's connection when the pane shows another one), selecting the entry once with `PreviousEntryName` (or like a created entry when the location is unchanged).

## Quick Search

Ctrl+F or File > Quick search (`CommanderActions.QuickSearch` for theme buttons) starts a quick search in the active pane in both front-ends, like Midnight Commander's and Total Commander's. `Find: <text>` is shown at the bottom of the pane.

- **Matching** (`QuickSearch` in Core): each typed character moves the cursor to the first matching entry in the pane's order. Matching is case-insensitive on the shown name (`DisplayName`, else `Name`), and `..` never matches. Only names starting with the text match; there are no wildcards, every character matches itself. A character that leaves nothing matching is rejected, so the text and cursor stay unchanged.
- **Keys:** Backspace removes the last character. Ctrl+F and Down go to the next match, Up to the previous one, wrapping around. Esc stops and keeps the cursor. Any other key stops and does what it always does, e.g. Enter opens the entry found and Tab switches panes. `+`, `-`, `*` and Space stop it only as the first character (they select entries), after that they're typed.
- **Stopping:** the quick search also stops when the pane is listed again (navigating, refreshing, sorting), when the focus leaves the pane and on a mouse click in the pane.
- Typing in a pane without Ctrl+F doesn't search: the command line and the selection keys use typed characters too, and the TUI's names start with a marker (Terminal.Gui's own type-ahead is turned off with `CollectionNavigator = null`).

## Properties

`GetPropertiesAsync(entries)` builds `EntryProperties`: a name and sections of `PropertyLine`s, similar to the properties of Windows Explorer, shown in the General tab, followed by the tabs of the plugins (`Tabs`, see [Tabs of plugins](#tabs-of-plugins)).

- **A single entry:** type (the Windows shell type name, elsewhere e.g. `TXT File (.txt)`), link target, location, size, size on disk (local files on Windows), contains (directories), and for local files the created/modified/accessed dates, other attributes (e.g. compressed or a link) and on Linux and macOS the permissions as `ls -l` shows them with the octal mode (e.g. `rwxr-xr-x (755)`, including setuid, setgid and sticky). Entries inside images and other volumes only have their modified date. `IEntry.Details` adds the volume's own type and sections (and `UsedFraction` as a bar), shown with `DisplayName`. Further sections show the Amiga name and the icon file with the lines its icon provider reads.
- **Check boxes** (`FlagGroups`): `Attributes` (the attributes the volume can change; for local files on Windows those of `LocalVolume.ChangeableAttributes`), for local files on Linux and macOS the permissions in three lines `Owner`, `Group` and `Others` with `Read`, `Write` and `Execute` (instead of attributes: .NET's read-only there is just the write permissions, and hidden is a name starting with a dot), changed with `File.SetUnixFileMode` keeping the other mode bits (setuid, setgid, sticky), and `Protection bits` (checked as the Amiga `List` command shows them, so `rwed` are checked when allowed). The protection bits are shown for every single entry while a plugin adds properties tabs (the Amiga plugin, like its Comment tab): entries without Amiga metadata or UAE metadata show `----rwed` (`EntryProperties.DefaultAmigaMetadata`), and changing them gives the entry UAE metadata with no comment, like adding a comment does (see the Comment tab below). A group can change when the volume can (`GetChangeableAttributes`, `CanSetAmigaMetadata`, or UAE metadata where entries can be moved); otherwise the boxes are disabled. When anything can be changed (`CanChange`: check boxes or texts of tabs) the dialogs have Save and Cancel (Esc cancels), otherwise only OK. Nothing is changed before Save, which calls `ChangePropertiesAsync(properties, checked, tabTexts)`: it changes only groups that differ, then saves the tabs whose text changed, and both panes are refreshed. Nothing else (e.g. the name) can be changed here.
- **Several entries:** the counts as name (e.g. `3 Files, 2 Folders`), `All of type ...` or `Multiple types`, `All in ...`, sizes and contents.
- **Drives:** label and drive, type, file system (or not ready), used/free space and capacity with a bar; several drives are summed.
- Sizes are like Explorer, e.g. `1.17 MB (1,234,567 bytes)` (`SizeFormatter.FormatWithBytes`).
- When `HasContents`, the dialogs count contents with `CountContentsAsync` in the background while open (`Calculating...` until the first report; closing cancels). Local directories are read from the file system, skipping inaccessible directories and not following directory links; other locations use a volume of their own. The number of lines doesn't depend on the contents, so the dialogs only update values.

### Tabs of plugins

Plugins add tabs after the General tab of a single entry with `IPropertiesTabProvider` (see [`IPropertiesTabProvider`](plugin-api.md#ipropertiestabprovider)). Each `PropertiesTab` shows a text of the entry:

- **No text:** a message (e.g. `No comment`) and an add button (e.g. `Add comment`) showing an empty text field.
- **A text:** the text in a text box and a delete button (e.g. `Delete comment`), which hides the text box and shows the message and add button again.
- The text box has a fixed height and a vertical scroll bar when the text is longer: a few lines for a single-line text (in the TUI the rows its maximum length needs in the dialog's width, at most 3, as the `TextView` has no border and empty rows would look like a gap), more for multi-line texts. The buttons are right below the message or the text box, and the tabs have the same height in all cases. A single-line text (e.g. a comment) is wrapped and limited to `MaxLength` while typing (also when pasting in the TUI); the lines of multi-line texts (`IsMultiline`, e.g. tooltypes) aren't wrapped and scroll horizontally in the GUI. The TUI syncs a `ScrollBar` with the `TextView` itself, as Terminal.Gui's `TextView` has none. The GUI's tabs are at least as high as the General tab, so the dialog doesn't shrink when changing tab.
- The buttons are disabled and the text read-only when the tab can't be changed (`Save` is null), e.g. inside a read-only image or archive.
- Changes are kept in the dialog until Save. An empty text is no text, line breaks are `\n`, and `PropertiesTab.Save` is only called for tabs whose text changed, after the check boxes of the General tab. A provider failing to read its tabs is left out.

The Amiga plugin's `AmigaPropertiesTabProvider` adds:

- **Comment:** for every entry, at most 79 characters (the Fast File System's limit; UAE metadata could store 80). Saved with `IPropertiesContext.SetAmigaMetadata`, which keeps the protection bits of the General tab (the context's `AmigaMetadata` is updated when they are saved first):
  - In Amiga file systems (adfs, RDB partitions) the comment is written to the file system.
  - In other volumes, e.g. a local directory, it's stored as UAE metadata (`UaeMetadataUpdater.SetMetadataAsync`): an entry without metadata gets it in the UAE metadata format of the settings (a node in `_UAEFSDB.___` or a `.uaem` metafile, with the protection bits `----rwed`), existing metadata is updated in its own format, and metadata that is no longer needed (no comment, `----rwed` and the Amiga name is the name) is removed: its node (the `_UAEFSDB.___` file is deleted when no nodes are left) or its metafile.
  - The comment can't be changed with the UAE metadata format `None` or in read-only locations (ISO images, archives; lha/lzx archives show their comments).
  - The General tab doesn't show the comment.
- **Tooltypes:** for entries with an Amiga icon (`.info` file) in the same directory (the entry and the icon file itself), one tooltype per line. Only disk object icons can be changed in writable locations: saving rewrites the disk object with the new tooltypes and keeps the data after it (e.g. a GlowIcon) as it is. The tooltypes of a NewIcon image (after `*** DON'T EDIT THE FOLLOWING LINES!! ***` and the blank tooltype before it) aren't shown and are kept. The tooltypes of true color (PNG) icons are read-only.
